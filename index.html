CYPHER OS

An engineering AI assistant: from a plain-language idea to a checked design.

Goal

Build an AI-powered engineering platform that turns plain-language ideas into structured requirements, editable CAD models and computational analysis within one connected workflow.

Challenges

Keeping requirements, geometry and analysis consistent as a project changes, and making every result something that can be inspected and judged on evidence.

Results

CYPHER OS is a working desktop prototype that takes a part described in plain language, typed or spoken, through requirements, CAD and analysis. In a recorded run on 14 Nov 2026, a spoken request for a 100 mm cantilever became a delivered, analysis-checked part 116.6 s after the spoken confirmation.

All 89 benchmark checks run so far pass. These are screening results, not engineering validation, and most of the planned verification has not run yet.

WooZOOM MK1 was a physical demonstration of the workflow. A folding flying-umbrella concept reached a 102-part assembly with no interferences in its flight, mid-fold and stowed states; CYPHER did not design it on its own; its parts were specified by hand.

How CYPHER OS works inside is not published here.

WooZOOM MK1

Modular push-style desktop wind tunnel.

Goal

Design and build a compact, modular wind tunnel around a WooZoo desk fan to make airflow visualization and hands-on aerodynamic experimentation more accessible.

Challenges

The biggest challenges were conditioning the fan's airflow, producing a useful fog stream, and making the assembly practical to print and modify. Early mist injection caused condensation, uneven dispersion and clogging, which forced changes to the visualization setup.

Solution & results

WooZOOM MK1 is an open-circuit tunnel driven by an 8-inch WooZoo desk fan: a conditioning housing with two hexagonal honeycomb inserts, a contraction, a clear-walled test section and an outlet diffuser, built from printed PLA parts. The initial CAD was AI-assisted in CYPHER OS (13 modules, 62 bodies over 1,200 mm; the later revision contracts 4:1 into a 101.6 mm test section). I reviewed and corrected it, then printed and assembled the tunnel. The build leaves out the CAD's mesh screens and uses my own fog inlet; its test-section size has not been measured.

The fog system took three tries. A single water-mist barrel worked at first; a triple-barrel collector clogged as liquid built up; a heated fog machine feeding a 10-outlet rake gave a clear, continuous stream. I added vertical positioning for the outlet.

The result is a working desktop prototype for qualitative flow visualization, shown here with a printed B-2-style flying-wing model, and a 29-page write-up with 26 references. No airspeed has been measured yet. Next: independent horizontal and vertical injector movement, better fog delivery, and load-cell force measurements after Mark 2.

AXYS Labs

Two-axis thrust-vector-control (TVC) lab for students.

Goal

Create an interactive engineering platform that helps students explore rocket design and thrust-vector control through virtual assemblies, simulation, and accessible control-system tools.

Challenges

The main challenge was bringing component selection, two-axis control and simulation results into a workflow that beginners could understand, while keeping enough technical depth for real experimentation.

Solution & results

AXYS Labs is a browser workspace with eight steps: Parts, Build, Models, Simulate, Code check, Stress tests, Compare and Report. Three learning modes (Explorer for high school, Engineer for college, and Research Lab) change the wording, never the physics. The part catalog has 91 entries (81 real parts and 10 illustrative), and each spec value carries its source.

The simulation is deterministic: Euler's equations with quaternions and fixed-step RK4 at 120 Hz, a gimbal model, PID or cascaded control, a ten-stage servo model (deadband, backlash, delay, lag, rate limit) and a noisy IMU with a complementary filter. Every run replays exactly from its seed and is graded PASS, MARGINAL or FAIL against fixed limits.

Code check generates the closed-loop control program and compares it with the reference simulator tick by tick: 4,862 of 4,862 checkpoints at 1e-12. The export is a software starter for a Linux computer such as a Raspberry Pi; running it on hardware is not yet verified. Initial student testing has begun in high schools in New Jersey, Georgia and India, and physical validation is the next stage.

PitPRO

Leak and overflow monitoring for concrete-washout pits.

Goal

Develop a low-cost monitoring system for temporary concrete-washout containment that can help identify potential leaks and overflows using liquid-level and environmental sensor readings.

Challenges

The biggest challenge is telling a genuine containment problem apart from normal changes in liquid level, surrounding conditions or sensor errors, with a sensor, power and communications layout that works for temporary installations.

Solution & results

I am co-developing PitPRO with another Embry-Riddle engineering student. Each pit gets nine sensing nodes: an internal node (liquid level from a magnetic angle sensor on a float reel, plus pH and temperature) and eight compass-point sentinels that read soil pH around the liner. They talk to one gateway over LoRa at 915 MHz, and only the gateway reaches the internet.

One ESP32 firmware source builds all three node roles. Every reading travels in a fixed 95-byte packet signed with a truncated HMAC-SHA256, stays in flash until the gateway returns an authenticated receipt, and is de-duplicated by node, boot and sequence, so retries cannot rewrite history. The dashboard runs the leak and overflow rules on simulated readings.

My work covered the system architecture, sensor placement and the enclosures: parametric CadQuery housings (a 160 × 160 mm sentinel and a 240 × 180 mm combined central box) with automated geometry checks. The firmware compiles for all three roles but no board has been flashed yet, and the detection thresholds are hypotheses to test in the field.

ISS SSEP Mission 22

Proposed experiment: grow potassium alum crystals in microgravity, then test them for CO₂ capture after flight.

Goal

Develop a microgravity research proposal investigating how potassium alum crystal growth and morphology compare with Earth-based controls, with a longer-term interest in evaluating treated materials for potential carbon-dioxide-capture applications.

Challenges

The main challenge was translating the research concept into a practical experimental assembly while accounting for hardware constraints, sample handling and repeatability. Inconsistent 3D prints also required repeated adjustments to the tube geometry and tolerances.

Solution & results

I am one of four student co-investigators on the proposal "Evaluating the CO₂ Capture Capacity of Space-Grown Potassium Aluminum Sulfate Crystals via Post-Flight Amine Impregnation". The experiment uses the program's three-volume mini-lab tube: 5.00 mL of 70 % isopropyl alcohol and 10.00 mL of alum solution at 68.0 g/L (680 mg, about 74.7 % of saturation at 15 °C), kept apart until a crew member would open valve A 14 days before undocking. The alcohol acts as an antisolvent (23.3 % v/v after mixing), so crystals would form without heating or cooling in orbit.

Back on Earth, flight and ground crystals would get identical treatment: a chilled-ethanol rinse, 4 h at 150 °C, a 2 h soak in 10 wt % polyethylenimine, then SEM, XRD and a 1000 ppm CO₂ breakthrough test.

I focused on the CAD of the experiment tube, a 290 mm, Ø12 / Ø10 mm replica of the RhFET-01 with two keyed ball valves. It went through three design iterations and seven rounds of tolerance refinement, and I printed six tubes for Earth-based testing. The research was presented at Embry-Riddle's Research Symposium; the flight investigation itself remains proposed work.

AP3X

Computational engineering model (CEM).

Goal

Develop a standalone computational engineering model that sizes, generates and verifies manufacturable designs from engineering requirements, with every input, unit, assumption and result traceable.

Challenges

The main challenge is one reusable calculation core for many problem types. It must keep units consistent, enforce each model's assumptions, separate numerical error from model error, and report when no design meets the requirements instead of relaxing them.

Solution & results

AP3X treats equations as typed data rather than code: a restricted expression tree with unit and quantity-kind checks (a moment is a torque, not an energy), compiled into an inspectable plan and run by bounded solvers. The working foundation has four packages: a cantilever beam with lightest-feasible sizing, an axial bar, a spring-mass-damper with its own energy ledger, and an electrothermal resistor model.

Each run reports its verdicts separately: whether it executed, whether it passed its numerical and admission checks, and whether it met the requirements. Physical validation and human approval are tracked as statuses of their own: physical validation stays "not established" and human approval "not granted" until real data and a reviewer's sign-off exist. When nothing fits, it returns "no feasible design".

The axial bar was added through the public interface while the core source was hash-frozen, which showed the core is reusable. The automated suite reached 2,148 passing tests, and 126 cases of a planned 1,080-case qualification program have passed so far (1 fail, 1 blocked, the rest not yet run).

Next is a standalone CEM with CAD generation, structural, thermal and flow simulation, convergence-based verification and optimisation. Its CalculiX groundwork already shows why verification matters: on a 100 × 20 × 4 mm steel cantilever the beam formula over-predicts the converged 3-D deflection by 1.48 %, while the mesh error is 0.014 %. The workflow in FIG AP3X-1 is theoretical and under development.

SpikePRO

Track and field spike-shoe cover.

Goal

Create a protective cover for track spikes that keeps exposed pins away from people and surfaces outside competition. Without one, athletes walk on their heels with their toes up, which strains the shins and wears the shoe.

Challenges

The main challenge was turning the first concept into a practical product through repeated design revisions while managing prototyping and production costs. Limited funding and tariffs later made it harder to scale manufacturing.

Solution & results

SpikePRO is a two-part printed cover: a spike cap over the forefoot plate, with an EVA pad filling the gaps between the pins, and a heel cap on an EVA base. One woven elastic lace makes four runs between the caps and meets at a lace lock under the spike cap. Off the shoe, the elastic pulls the caps into a compact bundle; stretched over a shoe, it clamps them on, and the lock sets the tightness.

As founder, I took the product through 27 design iterations, from yellow wedge caps with bungee cord to the black, purple-laced version shown in the patent drawings and the worn M7 and M8 models. Covers are scaled per athlete and printed in small batches. I sold 13 units locally and secured a confirmed 100-unit reseller order; larger-scale fulfillment was limited by funding, production costs and tariffs.

I filed a U.S. provisional utility patent application for the invention (No. 63/739,015, December 2024). The project taught me how manufacturing decisions, funding and customer demand shape the move from a prototype to a product.

VEDA

A shared workspace where several people run Claude- and OpenAI-backed workers on one versioned project record.

What it does

The model for every AI turn is chosen by hand. Missions run in numbered stages, and the next stage opens only after the current stage's required results are accepted. Proposed results ("candidates") stay separate from accepted revisions, and everything carries its provenance.

Results

Prototype 1 (Node 24 and TypeScript) has a SQLite schema of 31 tables, passkey invitations, project channels and a live adapter to the Codex App Server with tool networking and fallback disabled; 347 unit and 112 browser tests passed. Prototype 2 uses only the Python standard library: an append-only record store with 12 record types, a transactional outbox, lease-fenced run attempts and an acceptance transaction bound to an exact candidate digest. 726 tests and 183 browser page checks pass.

A UI ledger tracks all 147 planned controls honestly (33 implemented so far). Neither build is a finished desktop product yet, and the three-person pilot has not run.

DBOT

Verified file transfer from AI assistants to Discord.

What it does

Tell Claude or ChatGPT "send them over to <server>" and that assistant's own Discord bot posts the files into its thread, downloads them again and returns a per-file SHA-256 receipt. A file counts as delivered only when the re-downloaded copy matches.

Results

Files up to 10 GB are split into 20 MB pieces (at most 500), and each piece is verified. Interrupted sends resume, and deterministic nonces plus marker lines make retries duplicate-free. A 12-case failure matrix runs against a local fake Discord, from lost replies to expired download links and revoked tokens.

It was live-tested from Claude Code, Claude desktop, Codex and regular ChatGPT (through OpenAI's Secure MCP Tunnel): a 65 MB file in 4 pieces verified in 120–144 s. Releases build byte-for-byte reproducibly. Windows support and reboot auto-start are not yet verified.
